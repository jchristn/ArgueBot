# Scoped authorization implementation

Status: the pure evaluator, stored role/permission/assignment schema, protected built-in seeding and current user grant resolver are implemented. Permission/mapping/assignment administration endpoints, credential resolution, effective-permission endpoints and complete route/domain integration remain in progress under P2. The current HTTP service still enforces its documented compatibility roles, explicit administrator flags and ownership rules. Stored role management uses the existing authenticated transport; no new authentication scheme is introduced.

`AuthorizationEvaluator` consumes current authenticated principal facts, an operation target resolved by the service, and expanded grants. Those facts must come from trusted authentication and database resolution. A request body cannot select its own principal kind, administrator flag, active status, resource owner or target tenant. The resolver must combine activity checks for the user, tenant, credential, role, assignment, permission and mapping before producing active grants.

Ordinary user and credential decisions stay inside the authenticated tenant. Platform operations require an explicitly authenticated system administrator. Tenant administrator flags bypass permissions only inside their tenant. System administrator bypass is explicit in the returned decision so the integrating pipeline can audit it. Administrator flags on a credential describe its owner ceiling; they never grant a machine credential a direct administrator bypass.

Within a scope, any matching active Deny wins over every matching Permit, independently of ordering. No matching permit is an implicit deny. `Write` expands to Create, Update and Delete; all three must be permitted, and a denial of any one denies the aggregate. Write does not grant Execute or Admin. Resource type and operation names match without culture-dependent casing; opaque identifiers remain case sensitive.

Tenant assignments reach child resources only when inheritance is enabled. Without inheritance, they cover tenant metadata, including an explicit target tenant ID, and do not grant collection creation or child reads merely because a child ID is not allocated yet. Resource assignments require one exact authorization scope ID. The operation map may deliberately anchor a run operation to its parent conversation, but it must do so consistently for every transport. A permission cannot choose that anchor from an arbitrary request field.

A narrowing ownership condition is available for compatibility grants that retain the existing owned-data behavior. Its owner value must be read from the actual resource or selected from a validated creation identity. This does not replace tenant/resource assignment scope. Future collection queries must derive matching row predicates from the same grants; permission to read one resource must not expose tenant-wide counts, search hits or metadata.

Credential authorization intersects its own grants with the owning user's current authority. Empty credential grants deny access even when the owner is an administrator. Owner denial or missing owner permission constrains a credential that otherwise has a permit. A system/tenant administrator owner can satisfy the ceiling within the credential's existing tenant boundary, but cannot remove a credential's own explicit deny or grant platform scope. Decisions retain matched grant IDs and distinguish direct bypass from an owner-ceiling bypass.

Malformed active grants in the target tenant and unknown operations fail closed. The evaluator bounds each principal and owner input to 4096 expanded grants. Inactive grants do not participate. This is a defensive evaluation limit, not permission truncation: exceeding it denies the operation rather than silently discarding rules.

The integration work continues in the existing plan: expose protected role/permission/mapping and scoped user-assignment management; provide credential assignments; migrate compatibility access explicitly; map every route/worker operation; derive tenant-aware list predicates; and expose server-computed effective permissions to web, terminal and console clients. Those gates require both supported database providers, negative direct-API tests and complete accounting before the current compatibility policy can be retired.

Database schema 12 stores roles, permissions, mappings and scoped user assignments. Eight global built-in definitions have null tenant IDs and protected flags: TenantAdmin, SecurityAdmin, Auditor, ResourceAdmin, Editor, Viewer, TenantMember and the empty Custom template. Initialization refreshes their baseline permissions while preserving existing role IDs. Custom definitions and assignments remain tenant-bound. This storage foundation does not yet migrate compatibility users or change conversation/run route authority.

`database.Authorization.ResolveUserAsync` reads current user/tenant activity and explicit administrator flags with assignments and mappings in one serializable read transaction. Context role/administrator claims never replace the database facts. A missing role GUID falls back to its stored name, then a missing built-in record can use its immutable baseline. An existing inactive role blocks fallback; inactive mappings and permissions confer no grant. ResourceAdmin requires exact resource scope. Editor covers conversation/message/run data and does not confer execution, endpoint configuration or administration. TenantMember narrows user-profile reads to actual ownership.

Resolution is uncached, so role, permission, mapping and assignment changes take effect on the next resolution. There is no stale cache to invalidate in this slice; versioned caching remains part of subsequent administration integration. At most 256 active user assignments and 4096 expanded grants are accepted. Overflow and malformed stored permission data fail closed. Grant IDs are stable SHA-256 digests of assignment and mapping identities, preserving decision provenance across portable recovery. Credential storage/resolution, authorization-change accounting, effective-permission HTTP inspection and route/list-query integration remain open. Ordinary current routes retain their existing compatibility checks until that integration is complete.

Role definitions can be browsed with `GET /v1.0/api/roles?search=...&pageNumber=1&pageSize=25` and read individually by ID. Search is literal and case insensitive, and pages include globally visible built-ins alongside the authenticated tenant's custom roles. All role administration currently requires current database system/tenant administrator flags; scoped SecurityAdmin integration remains pending. Context flags alone do not grant access, and writes recheck current activity/administrator flags inside their transaction.

`POST /v1.0/api/roles` accepts `name`, `active` and optional `cloneRoleId`. A clone copies accessible active permission mappings to the new tenant custom definition; protected global permissions remain shared immutable references. Built-in names are reserved without regard to case. `PUT /v1.0/api/roles/{roleId}` replaces custom name/activity under `expectedRevision`. Built-ins return `403 protected_role`, foreign custom IDs return 404, duplicate names and stale revisions return 409. Cloning is create-only. Deactivate custom roles rather than deleting historical references. Role creation/update and their audit events commit atomically. Permission/mapping/assignment editing and complete scoped enforcement remain in progress.

The console exposes `roles list [SEARCH] [PAGE]`, `roles show ID`, `roles create JSON|-|--file PATH` and `roles update ID JSON|-|--file PATH`. Create JSON may include `cloneRoleId`; update JSON requires `expectedRevision`. These commands use the authenticated role API. The dashboard Roles page and terminal Ctrl+O provide the same role-definition lifecycle. Both list/search/page built-ins and custom roles, clone existing definitions and edit custom names/activity. Built-ins expose cloning rather than an edit action.

Web role drafts survive revision conflicts; cancel, refresh the role list and reopen the current definition before reconciling changes. Viewer direct-page navigation exposes an access error without create/edit controls, while the API independently denies the request. Role forms include contextual field/action help and responsive light/dark layouts. TUIKit forms validate names, retain update revisions and preserve clone source identity; Ctrl+S saves and Escape cancels. These controls do not enable permission or assignment editing yet.
