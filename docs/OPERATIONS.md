# Local service operations

Current scope: backup archives, restore jobs and offline snapshot commands have been removed at user direction. Existing archive files are left untouched. Database migration safety snapshots remain internal. Earlier validation notes describe historical behavior.

The replacement service binds to 127.0.0.1 and owns its application home exclusively. Start it with `dotnet run --project src/ArgueBot.Server -c Release -- --home .run/home`. Distribution packages, full live-provider compatibility, and release acceptance remain unfinished.

Local console/TUI clients automatically attach through owner-readable `runtime/service.json` metadata or start a sibling service binary for the selected home. Source builds can locate the Release service output in the same checkout. `--server` always attaches explicitly; `--no-start` disables automatic startup. Background startup detaches the Unix session or creates a windowless Windows process, redirects startup messages to `logs/startup.log`, and leaves the service running when a client exits. Concurrent startup still relies on the exclusive home lock rather than PID metadata. The console's `service stop` uses the graceful shutdown endpoint; process supervisors may restart a stopped container according to their own policy.

Settings live in `arguebot.json` beneath the selected home. Configuration precedence is `--home`, `ARGUEBOT_HOME`, then the operating system profile's `.arguebot` directory. `--port` overrides the configured listener port for the process. The Settings page displays the effective port and whether the saved configuration requires restart. Save uses a revision precondition and atomic file replacement. Restart detaches HTTP clients, drains workers, releases ownership, and reloads configuration. In containers the process exits for a supervisor instead of launching a second copy. Keep an explicit port override in mind when testing a saved listener change.

SQLite is the default. Startup refuses a future schema instead of downgrading it, and a supported historical SQLite upgrade creates a backup first. PostgreSQL creates a protected logical snapshot before a supported upgrade. Portable database snapshots stream known tables, preserve Unicode and null/integer values, and verify format, ordering, row counts and SHA-256 before transactional restore. Do not point development fixtures at an existing installation.

Request history captures redacted JSON body prefixes, structured redacted headers, method, path, status, duration, sizes, correlation and trace IDs. Default capture limit is 32768 bytes per body and retention is thirty days. Retention runs after traffic, at most hourly, rather than on an idle timer. Non-JSON bodies and SSE bodies are omitted. Query strings are excluded. The normal list loads metadata; body and header detail requires a separate detail request. History remains diagnostic data and can contain user conversation content.

## Local diagnostics

ArgueBot runs without Grafana, Prometheus, Loki, Tempo or a collector. No telemetry export endpoint or Docker stack is configured. The dashboard provides built-in request history and activity charts. Local JSONL operational logs remain in `logs/operations.jsonl`, with four rotated files and a 5 MiB rotation threshold. Capture failures use a separate best-effort type-only log. `stop-web.sh` and `stop-web.bat` stop only the selected ArgueBot service.

The service owns both its home and its selected database. SQLite holds an owner-only sibling `*.arguebot-owner` lock file, so different homes cannot accidentally run the same database. Leave the file in place; its presence alone does not indicate a live owner. PostgreSQL keeps a nonpooled advisory-lock session and uses that same connection for every write. A second service is refused. Losing the writer session cancels the host ownership signal, stops workers and exits with failure; it never transparently reconnects beside a successor. Use a dedicated PostgreSQL database for each ArgueBot instance. Generation attempts add atomic checkpoints and explicit uncertain-work recovery. Hosted process isolation remains a separate unfinished gate.

Windows background service launch uses a detached native process with an explicit inherited-handle whitelist containing only the null device. Capturing clients must not lend their stdout/stderr pipes to the service. The implementation follows the documented [Win32 handle-list attribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute). The console smoke captures process output and uses an isolated home containing spaces, Unicode and a trailing separator to exercise process lifetime and quoting on every runtime CI platform.

Operational diagnostics use Request history, service logs and execution attempt history. The product has no security-audit, user or role administration API.

History compatibility uses attachment protocol 2, independent of database schema 13 and the unchanged product version. Stop protocol-1 services with a matching client or authenticated shutdown request before replacing binaries; protocol-2 local clients refuse an incompatible listener. History previews default to 4096 Unicode code points per message, configurable through HistoryPreviewCodePoints with range 128 through 16384 after restart. Full-message reads and exports retain complete stored content.

Event retention is enabled by default and does not delete transcript messages or audit records. Settings exposes EventRetentionEnabled, EventRetentionDays (1..3650), EventMaxPerConversation (1..1000000), EventMaintenanceSeconds (5..3600), EventRetentionBatchSize (1..1000) and EventReplayPageSize (1..1000). Save and restart to apply. Disabling maintenance leaves existing events intact. Pruning preserves the latest sequence anchor even when it is older than the age limit. Replay-gap and pruned-event counters use bounded provider labels. Maintenance scans eligible conversation metadata in bounded batches and prunes each conversation in its own writer transaction.

## Sign-in operations

See [IDENTITY.md](IDENTITY.md) for the model. Operational notes:

- **Defaults.** Every startup creates the Default tenant, the default administrator (`admin@arguebot` / `password`) and the default token (`arguebotadmin`) if they are missing. A changed password, name or tenant name is never reset. Change the default password after the first sign-in.
- **Forgotten password.** A tenant or system administrator resets it: dashboard Users > Actions > Reset password, TUI Menu > Users, or `users password USER_ID` in the CLI. If every administrator is locked out, sign in with the default token `arguebotadmin` (it cannot be disabled) and reset the password from there.
- **Sign everyone out.** Stop the service, delete `secrets/session.key` in the application home and start it again. Every session token stops working; credential tokens keep working. To revoke one user's access, disable the user; to revoke a token, disable or delete its credential.
- **Back up** the `secrets` directory with the database: it holds the secret encryption keys, the session key (`session.key`) and the token key (`token.key`). Without `token.key`, bearer tokens and share links keep working but can no longer be revealed.
- **Audit retention.** Audit records are kept until an administrator deletes older ones (dashboard Audit log > Delete old records, or `DELETE /v2.0/api/audit?beforeUtc=...`). Deleting a tenant keeps its audit records.
- **Rate limits** are kept in memory: 10 failed sign-ins per address or email in 5 minutes, and 120 public share reads per address per minute. A restart clears them.
- **Remote access.** Set `listenAddress` to `0.0.0.0` (native installs listen on `127.0.0.1` by default), add host names to `allowedHosts` in `arguebot.json` or `ARGUEBOT_ALLOWED_HOSTS` (or `*` for any name, after changing the default password), restart, and serve over HTTPS. A request with an unlisted `Host` gets 403 `invalid_host`.


Schema-13 initialization accounts for repaired default assignments as `authorization.default_assignment_seed` with the System migration actor and no fabricated user identity. Identity changes use `user.default_assignment_sync` with the authenticated actor. Unchanged defaults produce no extra migration events. Protected assignments cannot be edited through assignment administration.

## Request activity

Request history offers rolling hour, day, week and 30-day chart ranges. They use 60 one-minute, 96 fifteen-minute, 84 two-hour and 90 eight-hour buckets respectively, including empty intervals. Bucket boundaries use UTC; axis and hover times use the browser timezone. Success is HTTP 100 through 399 (green); errors are HTTP 400 through 599 (red). Hover a bucket, or focus the chart and use Left/Right, Home/End and Escape for details. Refresh advances the chart window to the current time. Counts cover retained captures; retention settings determine how much history is available.

Dashboard assets with content hashes in their filenames use a one-year immutable browser cache. A new build changes asset URLs. HTML and API responses retain `Cache-Control: no-store`, so navigation and application data remain fresh. Request history records actual HTTP traffic, including assets; a logo used as both branding and a favicon may appear multiple times when first downloaded. Cached asset reuse does not make a new service request.

## Dashboard generation status

The conversation workspace shows a named agent activity indicator while a turn is executing, including before the agent returns text. The indicator reflects the service run state, not a process heartbeat or a guarantee that the upstream provider is responding. Reconnecting is shown separately when live updates are unavailable. Queued and pending-pause states have their own descriptions; paused and finished runs do not show an activity spinner.

Failed response cards display a failure warning and the matching generation attempt's saved error code, with a control to inspect generation attempts. The run summary retains its outcome above the transcript. Older CLI failures may retain only an exception type, such as `InvalidDataException`; their exact process output and exception details cannot be recovered from that code alone.

CLI process failures now retain bounded local evidence at `logs/runner-failures/<attempt-id>.json` under the selected application home. Each file links the conversation, run, attempt and response message to the provider, exception detail (including JSON parser paths), observed exit code, stdout/stderr tails and the triggering event when parsing or snapshot validation fails. Each text field retains at most 16384 UTF-16 characters; `Truncated` signals omitted output. The newest 100 captures are kept, with owner-only permissions and atomic file replacement. Raw output remains in these local files rather than public API error codes or ordinary operational log messages. Diagnostic write failures are logged by attempt ID and do not prevent the failed attempt checkpoint. Restart the service after rebuilding to enable capture in an already-running deployment. Existing discarded output cannot be reconstructed.

The TUI renders conversation previews and full-message readers with TUIKit Markdown. Headings, emphasis, lists, quotations, links, tables and fenced code use terminal styles and reflow to the available width. Code blocks preserve literal markup. Ctrl+L opens full history when a preview is truncated; rendering does not change saved or exported Markdown. Diagnostic and provenance readers retain plain text.

TUI New (Ctrl+N) creates a separate conversation through guided setup. Start debate (Ctrl+B) starts a new run in the selected conversation, retaining its history as context. New opens a blank question; Start debate prefills the first saved run question (or the conversation title before its first run), and keeps it editable; Review displays the exact question submitted for the new run. Going Back within setup or retrying a failed submission preserves that setup draft.

To ask another question after a debate, choose Follow-up in the TUI top action bar (Ctrl+Y). Select the respondent, then enter the question. The note composer adds context only and does not request an agent response.

New agent profiles default MaxOutputBytes to 67108864 (64 MiB), with an allowed range of 1024 through 67108864 bytes. This limit includes raw CLI protocol and tool output; REST runners apply it to captured answers. Existing profiles retain saved limits, and existing runs retain their frozen participant settings. Diagnostic files retain their separate bounded capture.

Failed turns show cause and recovery guidance directly in the dashboard response card and TUI transcript, including when an answer is partial. Generation attempts include an errorMessage field with the same safe explanation. Output overflows identify standard output, standard error or provider-answer limits and explain that tool/protocol output counts and Resume keeps frozen limits. Existing IOException attempts can recover an allowlisted capture explanation from their retained local diagnostic; missing or unreadable diagnostics show an explicit unknown-cause fallback. Raw stdout, stderr and provider payloads stay in local diagnostic files.

## Generation deadlines and interruptions

Participant `TimeoutSeconds` is a hard per-turn deadline, including CLI tool calls and time spent waiting for agent auditors. It defaults to 300 seconds and accepts 1 through 3600. A complex repository audit can legitimately exceed five minutes. The service terminates a CLI process tree when its deadline expires; receiving text or tool output does not extend the deadline.

New CLI and REST deadline failures pause the run with `generation_timeout` and finalize the attempt and partial response as failed. Both interfaces show safe cause and recovery guidance. Explicit interrupts, explicit stops and orderly service shutdowns preserve interrupted responses with distinct `generation_interrupted`, `generation_stopped` and `service_shutdown` attempt codes. Older interruptions without a cause retain an honest unknown-cause explanation. A restart/crash boundary still cannot prove whether external work happened.

The dashboard activity card shows elapsed wall-clock seconds from the accepted answer, the frozen participant timeout and the time this view has observed no answer-text change. This is a browser-clock estimate, not a heartbeat or evidence of upstream progress. Attempt inspectors show the historical timeout. Increasing a reusable participant timeout affects new runs; Resume keeps the original snapshot and may repeat external work.

Operational generation start/finish records include run, attempt and response IDs, with the provider and timeout at start and elapsed milliseconds at finish. Failure records include the safe failure code. Worker-level exceptions are logged by safe type/code rather than silently pausing. Request history describes HTTP success or failure, so a successful `202` run-acceptance response does not establish that its later generation succeeded.

CLI tool calls, nested auditor progress, successful process exit metadata and provider usage are not currently exposed as live product activity. CLI protocol data and nested reasoning must not be copied into the transcript as a substitute. Investigating those gaps requires correlated harness-side evidence; ordinary answer text and an SSE heartbeat alone do not prove tool progress. See [the monitored investigation](GENERATION_DIAGNOSTICS.md).

After rebuilding runtime binaries, shut down and start the service process to load the new assemblies. The Settings restart action drains workers and reloads configuration inside the existing process; it does not reload .NET assemblies. A refreshed dashboard can therefore display new frontend assets while still calling an older loaded runtime. Check the attempts response for the documented fields when verifying a runtime upgrade.

Credential master-key rotation is available through the web/TUI credential configuration and `credential-keys rotate EXPECTED_KEY_ID`. Preserve the entire protected secrets directory, including `credential.keys.json` after rotation, separately from database backups. Previous keys are retained for recovery and old backups; key rotation does not change credential values or their revisions. See [the multi-agent guide](MULTIPLE_AGENTS.md).
