# Local service operations

Current scope: backup archives, restore jobs and offline snapshot commands have been removed at user direction. Existing archive files are left untouched. Database migration safety snapshots remain internal. Earlier validation notes describe historical behavior.

The replacement service binds to 127.0.0.1 and owns its application home exclusively. Start it with `dotnet run --project src/ArgueBot.Server -c Release -- --home .run/home`. Distribution packages, full live-provider compatibility, and release acceptance remain unfinished; see [ROADMAP.md](../ROADMAP.md).

Local console/TUI clients automatically attach through owner-readable `runtime/service.json` metadata or start a sibling service binary for the selected home. Source builds can locate the Release service output in the same checkout. `--server` always attaches explicitly; `--no-start` disables automatic startup. Background startup detaches the Unix session or creates a windowless Windows process, redirects startup messages to `logs/startup.log`, and leaves the service running when a client exits. Concurrent startup still relies on the exclusive home lock rather than PID metadata. The console's `service stop` uses the graceful shutdown endpoint; process supervisors may restart a stopped container according to their own policy.

Settings live in `arguebot.json` beneath the selected home. Configuration precedence is `--home`, `ARGUEBOT_HOME`, then the operating system profile's `.arguebot` directory. `--port` overrides the configured listener port for the process. The Settings page displays the effective port and whether the saved configuration requires restart. Save uses a revision precondition and atomic file replacement. Restart detaches HTTP clients, drains workers, releases ownership, and reloads configuration. In containers the process exits for a supervisor instead of launching a second copy. Keep an explicit port override in mind when testing a saved listener change.

SQLite is the default. Startup refuses a future schema instead of downgrading it, and a supported historical SQLite upgrade creates a backup first. PostgreSQL creates a protected logical snapshot before a supported upgrade. Portable database snapshots stream known tables, preserve Unicode and null/integer values, and verify format, ordering, row counts and SHA-256 before transactional restore. Do not point development fixtures at an existing installation.

Request history captures redacted JSON body prefixes, structured redacted headers, method, path, status, duration, sizes, correlation and trace IDs. Default capture limit is 32768 bytes per body and retention is thirty days. Retention runs after traffic, at most hourly, rather than on an idle timer. Non-JSON bodies and SSE bodies are omitted. Query strings are excluded. The normal list loads metadata; body and header detail requires a separate detail request. History remains diagnostic data and can contain user conversation content.

## Local diagnostics

ArgueBot runs without Grafana, Prometheus, Loki, Tempo or a collector. No telemetry export endpoint or Docker stack is configured. The dashboard provides built-in request history and activity charts. Local JSONL operational logs remain in `logs/operations.jsonl`, with four rotated files and a 5 MiB rotation threshold. Capture failures use a separate best-effort type-only log. `stop-web.sh` and `stop-web.bat` stop only the selected ArgueBot service.

The service owns both its home and its selected database. SQLite holds an owner-only sibling `*.arguebot-owner` lock file, so different homes cannot accidentally run the same database. Leave the file in place; its presence alone does not indicate a live owner. PostgreSQL keeps a nonpooled advisory-lock session and uses that same connection for every write. A second service is refused. Losing the writer session cancels the host ownership signal, stops workers and exits with failure; it never transparently reconnects beside a successor. Use a dedicated PostgreSQL database for each ArgueBot instance. Generation attempts add atomic checkpoints and explicit uncertain-work recovery. Hosted process isolation remains a separate unfinished gate.

Windows background service launch uses a detached native process with an explicit inherited-handle whitelist containing only the null device. Capturing clients must not lend their stdout/stderr pipes to the service. The implementation follows the documented [Win32 handle-list attribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute). The console smoke captures process output and uses an isolated home containing spaces, Unicode and a trailing separator to exercise process lifetime and quoting on every runtime CI platform.

Operational diagnostics use Request history, service logs and execution attempt history. The product has no security-audit, user or role administration API.

History compatibility uses attachment protocol 2, independent of database schema 13 and the unchanged product version. Stop protocol-1 services with a matching client or authenticated shutdown request before replacing binaries; protocol-2 local clients refuse an incompatible listener. History previews default to 4096 Unicode code points per message, configurable through HistoryPreviewCodePoints with range 128 through 16384 after restart. Full-message reads and exports retain complete stored content.

Event retention is enabled by default and does not delete transcript messages or audit records. Settings exposes EventRetentionEnabled, EventRetentionDays (1..3650), EventMaxPerConversation (1..1000000), EventMaintenanceSeconds (5..3600), EventRetentionBatchSize (1..1000) and EventReplayPageSize (1..1000). Save and restart to apply. Disabling maintenance leaves existing events intact. Pruning preserves the latest sequence anchor even when it is older than the age limit. Replay-gap and pruned-event counters use bounded provider labels. Maintenance scans eligible conversation metadata in bounded batches and prunes each conversation in its own writer transaction.

The product has no tenant identities, account administration, pairing or sign-in. See [open workspace scope](IDENTITY.md).


Schema-13 initialization accounts for repaired default assignments as `authorization.default_assignment_seed` with the System migration actor and no fabricated user identity. Identity changes use `user.default_assignment_sync` with the authenticated actor. Unchanged defaults produce no extra migration events. Protected assignments cannot be edited through assignment administration.

## Request activity

Request history offers rolling hour, day, week and 30-day chart ranges. They use 60 one-minute, 96 fifteen-minute, 84 two-hour and 90 eight-hour buckets respectively, including empty intervals. Bucket boundaries use UTC; axis and hover times use the browser timezone. Success is HTTP 100 through 399 (green); errors are HTTP 400 through 599 (red). Hover a bucket, or focus the chart and use Left/Right, Home/End and Escape for details. Refresh advances the chart window to the current time. Counts cover retained captures; retention settings determine how much history is available.

Dashboard assets with content hashes in their filenames use a one-year immutable browser cache. A new build changes asset URLs. HTML and API responses retain `Cache-Control: no-store`, so navigation and application data remain fresh. Request history records actual HTTP traffic, including assets; a logo used as both branding and a favicon may appear multiple times when first downloaded. Cached asset reuse does not make a new service request.
