# Backup and recovery during replacement development

The replacement service supports SQLite and PostgreSQL snapshots and complete recovery archives. A complete archive can move history between either provider. Controlled restore always creates a new application home and leaves the recovered service stopped. PostgreSQL destinations must be explicitly provisioned and empty. Backup upload/import, retention scheduling, full hosted security and remaining interface parity are still open in IMPROVEMENTS.md. Keep the legacy application available until the product gates pass.

Open Dashboard > Backups as a system administrator. Create an archive with a recognizable name. Supply an optional passphrase of at least twelve characters to encrypt it. Selecting session encryption keys and literal connection credentials requires encryption; environment secret values are never included. Keep the passphrase separately. The service cannot recover it. Without encryption, an archive contains readable conversation and request history and must be kept private.

Creation returns an operation identifier immediately. The service continues after the browser or console disconnects. Poll its status until completed or failed. A ready artifact records its byte length and SHA-256 digest. Download uses the authenticated connection, with no token in the URL. Verify checks decryption, the strict inventory, checksums and snapshot/schema compatibility without changing live data. A failed verify preserves the original artifact. Missing environment credential references are reported by name for operator reconfiguration.

Restore requires a new home name and optionally a listener port and destination provider. The new home is beneath the running service home's restores directory. SQLite creates a database file there. For PostgreSQL, first provision a dedicated empty database and set a connection-string environment variable on the service machine. Supply only that variable's name as restoreConnectionEnvironmentVariable. Existing homes and PostgreSQL databases containing any user table are refused before schema mutation. The active service is unchanged.

The service validates the archive before restoring its relational snapshot, migrates historical schemas, reconciles uncertain work, revokes restored sessions and rotates restored issuing keys. Its final operation records the effective port. Inspect retained source settings, restore required environment credentials and deliberately start the separate recovered home when ready. Local process identities and CLI session caches are regenerated for the new home; they are never copied from an archive.

PostgreSQL database commit and filesystem publication span separate resources. If database restoration commits but later reconciliation or home publication fails, the operation fails with restore_publication_failed and reports retainedStagingHome. Preserve that owner-protected directory and the destination database. A runtime/recovery-incomplete marker prevents accidental startup when reconciliation did not finish. Review the retained manifest, portable snapshot, destination connection reference and session/run state before completing recovery. Do not blindly remove the marker or retry against the populated database. A reconciled staging home whose publication alone failed can be moved to an absent intended destination while all related services remain stopped. If initialization or the database restore transaction fails before commit, a newly initialized PostgreSQL schema may remain; use a fresh empty fixture/database for another attempt. Recovery never drops an existing database automatically.

The console exposes the same operations. Supply passphrases through stdin or an owner-readable request file rather than shell history. For an isolated development home:

```sh
printf '%s' '{"name":"Before configuration changes","includeSecrets":false}' |
  dotnet run --project src/ArgueBot.Cli -c Release -f net10.0 -- --home .run/home backups create -
dotnet run --project src/ArgueBot.Cli -c Release -f net10.0 -- --home .run/home backups list
dotnet run --project src/ArgueBot.Cli -c Release -f net10.0 -- --home .run/home backups operations
```

Use returned identifiers in backups status OPERATION, backups download BACKUP NEW_FILE, backups verify BACKUP --file REQUEST_FILE, backups restore BACKUP --file REQUEST_FILE and backups delete BACKUP. A verify request is an empty object for an unencrypted archive or an object with password. A PostgreSQL restore request has destinationName, restoreDatabaseType set to Postgresql, restoreConnectionEnvironmentVariable and optionally port/password. The variable must already exist in the service process environment. Acceptance is not completion: inspect the durable result. Interrupted jobs fail visibly and require explicit operator action; they are never silently replayed.

Ctrl+K opens the same administrator recovery workflows in the TUI. Passphrases are masked; PostgreSQL selection exposes the connection-reference field. Browse durable operations to refresh status after reconnecting. The dashboard and console expose the same paginated job inventory, including earlier client sessions.

Offline server maintenance flags remain useful for database-only snapshots: --export-snapshot FILE, --verify-snapshot FILE, and --home EXPLICIT_HOME --restore-snapshot FILE. Snapshot restore is transactional, keeps a pre-restore snapshot and revokes restored sessions after migration. These files omit settings and keys. Do not treat them as complete archives or run offline mutation beside an active service. See [operations](OPERATIONS.md) and [API reference](../REST_API.md).

An HTTPS listener certificate at `keys/listener.pfx` is private key material. Default archives omit it. Encrypted archives with explicit secret inclusion can retain it, bounded to one MiB; password environment values are never copied. Restored HTTPS configurations without a retained certificate require operator provisioning before startup. This does not start or alter the original listener.
